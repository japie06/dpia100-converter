# DPIA100 field layout

Technical reference for the DPIA100 import file as produced by `dpia100.ps1` and by the web version
`dpia100.html` (same rules, byte-identical output; both are tested on every case in `tests/cases`).

**Sources** (the PDFs are copyrighted and not included in the repo)
- `docs/DPIA100 record indeling.pdf`: Beaufort help, "Mutatiebestand maken (importeren)", Visma 2024-08.
- `docs/Microsoft Word - Handboek DPIA100 via Excel.doc.pdf`: Raet handbook, version 20050101.
- A file generated by the official Excel tool, which the script output matches byte for byte (see
  [Verified example](#verified-example)).

## File format

| Property | Value |
|---|---|
| File name | Must start with `DPIA100`, otherwise Beaufort does not find it (owner; case does not matter, `dpia100.txt` works). The script rejects other names (decision 12) and by default writes `DPIA100_<csv name>.txt` next to the input CSV (decision 13). The web version suggests the same name in its save dialog and refuses a chosen name that does not start with `DPIA100`. Location settings: `IMP_FILE` / `IMP_PAD`, or `Beaufort.asn` |
| Location | Beaufort *files* folder, default `...\Raet\Beaufort <versie>\files\` |
| Encoding | Windows-1252, single byte per character. UTF-8 shifts columns after `ö`, `é` etc. |
| Record length | Exactly 187 characters = 187 bytes |
| Line ending | CRLF, also after the last record |
| Header / trailer | None |

What Beaufort does with deviating files (probe rounds 1-2, `tests/beaufort/findings.md`):
- It reads line by line. LF line endings also work, and a missing line break after the last line is fine.
- With CR-only line endings the records after the first are **lost without an error**.
- A blank line becomes an empty, rejected record.
- A UTF-8 file shifts every field after an accented character; a UTF-8 BOM breaks the first record.
- Duplicate records are both created.
- At import Beaufort also accepts lowercase codes, other alignments, leading zeros and lines of 186 or
  188 bytes. The script still follows the docs and the Excel-tool layout (owner decision).

## Record layout

| Pos | Len | Field | Format in this script | Source |
|---|---|---|---|---|
| 1-3 | 3 | Procescode | Uppercase alphanumeric, left-aligned (`CMT`) | docs |
| 4-9 | 6 | Rubriekcode | Uppercase alphanumeric, left-aligned (`E00101`) | docs |
| 10-59 | 50 | Object_id | See [Object_id](#object_id), left part fixed width, padded to 50 | docs + Excel tool |
| 60 | 1 | Indicator stam/variabel | `S` or `V` | docs |
| 61-71 | 11 | Creatiedatum | 3 spaces + `ddMMyyyy` | docs + Excel tool |
| 72-87 | 16 | Creatiegebruiker | Right-aligned, space padded | Excel tool |
| 88-137 | 50 | Waarde (mutatiewaarde) | Left-aligned, space padded | docs |
| 138-148 | 11 | Ingangsdatum | 3 spaces + `ddMMyyyy` | docs + Excel tool |
| 149-178 | 30 | *(not documented)* | 30 spaces | Excel tool only |
| 179-181 | 3 | Productiesoort | `NOR` | docs |
| 182-187 | 6 | Verrekenperiode | 6 spaces (not implemented) | docs |

**Positions 149-178** are not described in either PDF. The documented fields end at Ingangsdatum
(148), and Productiesoort starts at 179. The Excel tool fills them with spaces.

## Field rules

### Procescode
Uppercase. Must be defined in Beaufort as *code proces* of an aanleverend proces (200502). Codes
already in use: AAK, CON, TMT, CMT, RVM.

### Rubriekcode
Standard or custom rubriek. The 2024 help says uppercase only, while the 2005 handbook allows both. The
script uppercases.

### Object_id
Compound key; parts separated by **one space**, **no leading zeros**. Which parts are required
depends on the gegevenssoort of the rubriek:

| Gegevenssoort | Parts | Supported |
|---|---|---|
| PS Persoon | pers_nr | yes |
| DV Dienstverband | pers_nr dv_vlgnr | yes |
| BG Bank-giro | pers_nr dv_vlgnr bg_vlgnr | no |
| IZ Inzet | pers_nr dv_vlgnr oe_oper_sl operfunc_kd ingang_dt | no |
| IP Inpastabel | reg_sal_kd inpas_nr | no |
| LV Loonverdeling | pers_nr dv_vlgnr lv_rglnr | no |
| SD Speciale doorbelasting | pers_nr dv_vlgnr sd_rglnr | no |
| ZG Ziektegeval | pers_nr dv_vlgnr zg_nr | no |
| ZT Ziektetijdvak | pers_nr dv_vlgnr zg_nr zt_nr | no |

Part lengths: pers_nr 6, dv_vlgnr 3, bg_vlgnr 2 (handbook: 1), lv_rglnr 3 (handbook: 2), sd_rglnr 2,
oe_oper_sl 10, operfunc_kd 7 (alfanumeriek), reg_sal_kd 2 (alfanumeriek), inpas_nr 4, zg_nr 10,
zt_nr 10, ingang_dt = Beaufort date.

**Alignment** (not in the docs; taken from Excel tool output):
- pers_nr is right-aligned in 6 positions.
- dv_vlgnr is right-aligned in 3 positions after the separating space.
- The rest of the 50 positions are spaces.

| Key | Positions 10-20 |
|---|---|
| PS 123 | `   123     ` |
| DV 123 / 1 | `   123   1 ` |
| DV 123450 / 1 | `123450   1 ` |

The alignment of the unsupported parts is unknown. Check output from the Excel tool before adding
them.

### Indicator stam/variabel
`S` (stamgegeven) or `V` (variabel gegeven). It must match the rubriek in the Beaufort rubriektabel.
The script also accepts `STAM` / `VARIABEL` as input.

### Creatiedatum and Ingangsdatum
Beaufort accepts `ddmmeejj` (`01011996`), `dd-mm-eejj` (`01-01-1996`) and `ddmmjj` (`010196`). The
script always writes `ddmmeejj`, right-aligned in 11 positions.

A future ingangsdatum is allowed, but Beaufort only processes the mutation once that date is
reached. Processing (100252) selects on "ingangsdatum t/m", which must be today or earlier.

Accepted input formats in the CSV: `d M yyyy`, `dd MM yyyy`, `d-M-yyyy`, `dd-MM-yyyy`,
`d/M/yyyy`, `dd/MM/yyyy`, `yyyy-MM-dd`, `ddMMyyyy`, and day-month-year with mixed separators (`.`,
`-`, `/`, space). Impossible dates such as 31-02 are rejected.

### Creatiegebruiker
Alphanumeric, max 16. The user must exist in Beaufort. If *gebruikersautorisatie* is on for the
aanleverend proces, only this user can review and process the mutations.

### Waarde
- Left-aligned; leading zeros are allowed.
- Must satisfy the rubriek's rules in the rubriektabel, and appear in the referentietabel if the
  rubriek has one.
- Amounts: a minus sign at position 88 and a **decimal point**.

Beaufort behaviour (probes P08, `tests/beaufort/findings.md`): the import (100254) accepts any value.
Processing (100252) rejects a comma in a numeric rubriek (PI_2229) and reads a dot as decimal point,
so `3.250` is processed silently as 3,25. Extra decimals are rounded (owner, seen with manual entry).

Script handling (decision 8). The script can't tell a numeric rubriek from a text rubriek, so it warns
instead of rejecting. With warnings, the file is only written after the user types `Y`. The CSV
delimiter hints at the notation: Dutch Excel saves with `;` and a decimal comma, English Excel with `,`
and a decimal dot; a tab gives no hint.

| Value | `;` file (Dutch) | `,` file (English) | Tab file |
|---|---|---|---|
| `12,50`, `-12,50` | `12.50`, reported | `12.50`, warning | `12.50`, warning |
| `1,234` | `1.234`, reported | as typed, warning (means 1234) | `1.234`, warning |
| `3.250`, `12.345` | as typed, warning (formatted 3250?) | as typed, no warning | as typed, warning |
| `1.234,56`, `1,234.56`, `1.234.567` | as typed, warning | as typed, warning | as typed, warning |

"Reported" means listed in one line without asking for confirmation. `12.50`, `0.250` and dates with
dots (`1.11.2026`) always pass as-is without a warning.
- The value is normalized to NFC.
- Control characters (line breaks, tabs) and characters outside Windows-1252 are rejected.

Special characters (tested in `tests/cases/ok-chars-*` for every input encoding):
- Accepted, one byte each: all accented letters used in Dutch (`á à â ä é è ê ë í ì î ï ó ò ô ö ú ù
  û ü ç ñ ý ÿ` and capitals), `€ ’ ‘ “ ” „ – — … ½ ° § ß æ œ ø å Š Ž £`, and all ASCII punctuation.
- Letters typed as base letter + combining accent are combined first, so they still take one byte.
- Rejected with an error: characters outside Windows-1252, for example the `ĳ`/`Ĳ` ligature, Polish
  `Ł ł ę`, Turkish `Ş ş`, `ő`, `Ć`, Vietnamese `ễ`, Greek, `₂`, `→`, zero-width space and emoji.
  Write `ij` as two letters.
- How Beaufort itself handles each Windows-1252 character is being probed; see
  `tests/beaufort/findings.md`.
- Values over 50 characters are truncated with a warning.
- Dates, times and uppercase-only values are written as typed. The owner chose not to force a format
  on Waarde; Beaufort validates it against the rubriek.

The Excel tool's *Rubriek* tab assigns each rubriek a type that drives the value format:
`N` numeriek (default), `S` tekst, `D` datum, `T` tijd, `H` hoofdletters. The script has no rubriek
lookup.

### Productiesoort
The docs list `NOR` and `JWP`. The script supports `NOR` only; an empty value becomes `NOR`.

### Verrekenperiode
Format `ppjjjj` (pp = periode, jjjj = jaar), for example `132003`. Periods 13-15 are only applied if the
ingangsdatum is in December; otherwise Beaufort recalculates. For recalculation over a
jaarwerkperiode the ingangsdatum must equal the start of the last loonperiode. Not implemented:
always 6 spaces.
