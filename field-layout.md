# DPIA100 field layout

Technical reference for the DPIA100 import file as produced by `dpia100.ps1` and by the web version
`dpia100.html` (same rules, byte-identical output; both are tested on every case in `tests/cases`).

**Sources** (the PDFs are copyrighted and not included in the repo)
- `docs/DPIA100 record indeling.pdf`: Beaufort help, "Mutatiebestand maken (importeren)", Visma 2024-08.
- `docs/Microsoft Word - Handboek DPIA100 via Excel.doc.pdf`: Raet handbook, version 20050101.
- A file generated by the official Excel tool, which the script output matches byte for byte (see
  [Verified example](#verified-example)).
- The source of the official Excel tool (`DPIA100.xlsm`, VBA version V 06.12.6, 2005), reviewed in October
  2026 (local only, not in the repo). It shows how the tool built each field. It is 20 years old and has
  bugs (see [Excel tool](#excel-tool)), so it explains layout choices but is not the source of truth:
  Beaufort itself is (`tests/beaufort/findings.md`).

## File format

| Property | Value |
|---|---|
| File name | Must start with `DPIA100`, otherwise Beaufort does not find it (owner; case does not matter, `dpia100.txt` works). The script rejects other names (decision 12) and by default writes `DPIA100_<csv name>.txt` next to the input CSV (decision 13). The web version suggests the same name in its save dialog and refuses a chosen name that does not start with `DPIA100`. Location settings: `IMP_FILE` / `IMP_PAD`, or `Beaufort.asn` |
| Location | Beaufort *files* folder, default `...\Raet\Beaufort <versie>\files\` |
| Encoding | Windows-1252, single byte per character. UTF-8 shifts columns after `ö`, `é` etc. |
| Record length | Exactly 187 characters = 187 bytes |
| Line ending | CRLF, also after the last record |
| Header / trailer | None |

What Beaufort does with deviating files (probe rounds 1-2, `tests/beaufort/findings.md`):
- It reads line by line. LF line endings also work, and a missing line break after the last line is fine.
- With CR-only line endings the records after the first are **lost without an error**.
- A blank line becomes an empty, rejected record.
- A UTF-8 file shifts every field after an accented character; a UTF-8 BOM breaks the first record.
- Duplicate records are both created.
- At import Beaufort also accepts lowercase codes, other alignments, leading zeros and lines of 186 or
  188 bytes. The script still follows the docs and the Excel-tool layout (owner decision).

## Record layout

| Pos | Len | Field | Format in this script | Source |
|---|---|---|---|---|
| 1-3 | 3 | Procescode | Uppercase alphanumeric, 1-3 characters, left-aligned (`CMT`) | docs (length 3) |
| 4-9 | 6 | Rubriekcode | Uppercase alphanumeric, 1-6 characters, left-aligned (`E00101`) | docs (length 6) + owner |
| 10-59 | 50 | Object_id | See [Object_id](#object_id), left part fixed width, padded to 50 | docs + Excel tool |
| 60 | 1 | Indicator stam/variabel | `S` or `V` | docs |
| 61-71 | 11 | Creatiedatum | 3 spaces + `ddMMyyyy` | docs + Excel tool |
| 72-87 | 16 | Creatiegebruiker | Right-aligned, space padded | Excel tool |
| 88-137 | 50 | Waarde (mutatiewaarde) | Left-aligned, space padded | docs |
| 138-148 | 11 | Ingangsdatum | 3 spaces + `ddMMyyyy` | docs + Excel tool |
| 149-178 | 30 | *(not a field)* | 30 spaces | Excel tool |
| 179-181 | 3 | Productiesoort | `NOR` or `COR` | docs + owner |
| 182-187 | 6 | Verrekenperiode | 6 spaces (not implemented) | docs |

**Positions 149-178** are not described in either PDF. The documented fields end at Ingangsdatum
(148), and Productiesoort starts at 179. They are not a field: the Excel tool right-aligns productiesoort
in 33 positions, so these are its leading spaces.

## Field rules

### Procescode
Uppercase, length 3 (the PDF gives no alignment). Must be defined in Beaufort as *code proces* of an
aanleverend proces (200502). Codes already in use: AAK, CON, TMT, CMT, RVM. The script accepts 1-3
characters and left-aligns a shorter one; the Excel tool right-aligned it. All known codes have 3, so
the difference has not mattered.

### Rubriekcode
Standard or eigen (custom) rubriek, length 6 (the PDF gives no alignment). The 2024 help says uppercase
only, while the 2005 handbook allows both. The script uppercases and accepts 1-6 characters. Most codes
have 6, but the rubrieken export has shorter ones: the standard DV rubriek `SETKB` and eigen codes such
as `E0010`, `M01` and `WS100`. A shorter code is **left-aligned** (owner; what v1.2.0 did). The Excel tool
right-aligned it, and Beaufort has not been probed with one yet (#25).

### Standard rubrieken
The script and the page contain the standard PS/DV rubrieken of Beaufort (decision 17): the rubrieken
with *Fix* = `J` in the report *Overzicht rubrieken* (function 210006), about 4,200 of them. A
customer cannot change their gegevenssoort, type, length, decimals, stam/variabel or *Blok ind mut*
(Beaufort help *Rubrieken wijzigen of verwijderen*), so the list holds only these. Min/max and the values
of referentietabellen can be changed per customer and are left out. How the list is made and refreshed:
`docs/rubrieken-export.md`.

| Check | Standard rubriek | Any other code (eigen rubriek) |
|---|---|---|
| Dienstverband | DV rubriek: required (empty or `0` is an error, Beaufort PI_1650). PS rubriek: must be empty (decision 18) | Empty = PS key, filled = DV key |
| S of V | Must be allowed by the rubriek: stam only, variabel only, or both (decision 18) | `S` or `V` |
| Blok ind mut = `J` | Warning: cannot be imported through DPIA100 (decision 19). Blank counts as not blocked | - |
| Waarde | By type, see [Waarde](#waarde) (decision 20) | Decisions 8 and 16 |

A code that is not in the list is allowed without any message. Eigen rubrieken cannot be supplied yet
(#24).

### Object_id
Compound key; parts separated by **one space**, **no leading zeros**. Which parts are required
depends on the gegevenssoort of the rubriek:

| Gegevenssoort | Parts | Supported |
|---|---|---|
| PS Persoon | pers_nr | yes |
| DV Dienstverband | pers_nr dv_vlgnr | yes |
| BG Bank-giro | pers_nr dv_vlgnr bg_vlgnr | no |
| IZ Inzet | pers_nr dv_vlgnr oe_oper_sl operfunc_kd ingang_dt | no |
| IP Inpastabel | reg_sal_kd inpas_nr | no |
| LV Loonverdeling | pers_nr dv_vlgnr lv_rglnr | no |
| SD Speciale doorbelasting | pers_nr dv_vlgnr sd_rglnr | no |
| ZG Ziektegeval | pers_nr dv_vlgnr zg_nr | no |
| ZT Ziektetijdvak | pers_nr dv_vlgnr zg_nr zt_nr | no |

Part lengths: pers_nr 6, dv_vlgnr 3, bg_vlgnr 2 (handbook: 1), lv_rglnr 3 (handbook: 2), sd_rglnr 2,
oe_oper_sl 10, operfunc_kd 7 (alfanumeriek), reg_sal_kd 2 (alfanumeriek), inpas_nr 4, zg_nr 10,
zt_nr 10, ingang_dt = Beaufort date.

**Alignment** (not in the docs; taken from Excel tool output):
- pers_nr is right-aligned in 6 positions.
- dv_vlgnr is right-aligned in 3 positions after the separating space.
- The rest of the 50 positions are spaces.

| Key | Positions 10-20 |
|---|---|
| PS 123 | `   123     ` |
| DV 123 / 1 | `   123   1 ` |
| DV 123450 / 1 | `123450   1 ` |

The unsupported parts, as the Excel tool source builds them (never verified in Beaufort; probe before
adding). Each part is right-aligned in a fixed width that includes the separating space:

| Type | After pers_nr (6) and dv_vlgnr (space + 3) |
|---|---|
| BG | bg_vlgnr: space + 1 (list 1-8) |
| LV | lv_rglnr: space + 2 (list 0-20) |
| SD | sd_rglnr: space + 2 |
| IZ | oe_oper_sl: space + 10, operfunc_kd: space + 7, ingang_dt: 11 positions |

- These widths follow the 2005 handbook. The 2024 PDF allows bg_vlgnr 2 and lv_rglnr 3, which do not fit.
- For IZ the tool took the **mutation's** ingangsdatum in the Windows short-date format as ingang_dt.
  The PDF asks for the start date of the inzet in a Beaufort date format, so this is probably a bug.
- The tool had no IP, ZG or ZT: there is no reference layout for those.

### Indicator stam/variabel
`S` (stamgegeven) or `V` (variabel gegeven). It must match the rubriek in the Beaufort rubriektabel; a
rubriek can allow both. The script also accepts `STAM` / `VARIABEL` as input, and checks a standard
rubriek against the list (decision 18).

### Creatiedatum and Ingangsdatum
Beaufort accepts `ddmmeejj` (`01011996`), `dd-mm-eejj` (`01-01-1996`) and `ddmmjj` (`010196`). The
script always writes `ddmmeejj`, right-aligned in 11 positions.

A future ingangsdatum is allowed, but Beaufort only processes the mutation once that date is
reached. Processing (100252) selects on "ingangsdatum t/m", which must be today or earlier.

Accepted input formats in the CSV: `d M yyyy`, `dd MM yyyy`, `d-M-yyyy`, `dd-MM-yyyy`,
`d/M/yyyy`, `dd/MM/yyyy`, `yyyy-MM-dd`, `ddMMyyyy`, and day-month-year with mixed separators (`.`,
`-`, `/`, space). Impossible dates such as 31-02 are rejected.

### Creatiegebruiker
Alphanumeric, max 16. The user must exist in Beaufort. If *gebruikersautorisatie* is on for the
aanleverend proces, only this user can review and process the mutations.

### Waarde
- Left-aligned; leading zeros are allowed.
- Must satisfy the rubriek's rules in the rubriektabel, and appear in the referentietabel if the
  rubriek has one.
- Amounts: a minus sign at position 88 and a **decimal point**.

Beaufort behaviour (probes P08, `tests/beaufort/findings.md`): the import (100254) accepts any value.
Processing (100252) rejects a comma in a numeric rubriek (PI_2229) and reads a dot as decimal point,
so `3.250` is processed silently as 3,25. Extra decimals are not rounded up: `12.345` became 12,34
in a 2-decimal rubriek (probe round 4).

Script handling of amounts (decision 8), for an eigen rubriek and a standard numeric rubriek. For an
eigen rubriek the script can't tell a numeric rubriek from a text rubriek, so it warns instead of
rejecting. With warnings, the file is only written after the user types `Y`. The CSV delimiter hints at
the notation: Dutch Excel saves with `;` and a decimal comma, English Excel with `,` and a decimal dot; a
tab gives no hint.

| Value | `;` file (Dutch) | `,` file (English) | Tab file |
|---|---|---|---|
| `12,50`, `-12,50` | `12.50`, reported | `12.50`, warning | `12.50`, warning |
| `1,234` | `1.234`, reported | as typed, warning (means 1234) | `1.234`, warning |
| `3.250`, `12.345` | as typed, warning (formatted 3250?) | as typed, no warning | as typed, warning |
| `1.234,56`, `1,234.56`, `1.234.567` | as typed, warning | as typed, warning | as typed, warning |

"Reported" means listed in one line without asking for confirmation. `12.50` and `0.250` always pass
as-is without a warning. A date with dots (`1.11.2026`) is not an amount, but gets the date warning below.

Empty values, dates and times (decision 16, owner):
- An **empty Waarde deletes** the current value of the rubriek in Beaufort. It is written, with one
  warning listing the rows (every rubriek). The Excel tool only allowed an empty value through the
  keyword `NULL`.
- `NULL` is written as typed, like any other text (owner). The Excel tool turned it into an empty value.
- The Excel tool wrote a date in a date rubriek as `dd-mm-yyyy` and a time in a time rubriek as `hh:mm`.
  Beaufort also has time rubrieken of type `U` with `hh:mm:ss` (owner, confirmed in Beaufort). For an
  eigen rubriek, a value that looks like a date in another shape (`1-11-2026`, `1/11/26`, `2026-11-01`,
  `1 11 2026`, `1.11.2026`) or a time in neither shape (`8:30`, `8:30:00`) is written as typed, with a
  warning. The script cannot tell a date rubriek of an eigen rubriek from a text rubriek, so it never
  converts there. `01112026` and `8.30` are not recognized, because they may be numbers.

Standard rubriek, by type (decision 20, owner). The checks of decision 7 and the empty-value warning
apply as for any rubriek; then:

| Type | Handling | Error when |
|---|---|---|
| `N` numeric | The amount table above (comma conversion, warnings) | Not a number after the conversion (`abc`, `NULL`, `1.234,56`, English `1,234`, a date); more significant decimals than the rubriek has (`12.345` in a 2-decimal rubriek: Beaufort would store 12,34); more digits before the point than the length allows (the length includes the point and the decimals, so N 9,2 allows 6; confirmed in the Beaufort GUI, where N 4,2 rejects `12,34`) |
| `D` date | Written as `dd-mm-yyyy`, reported in one line (no `Y` needed). Accepts the Ingangsdatum shapes (`1-11-2026`, `2026-11-01`, `01112026`, `1.11.2026`, ...) | Not a date: `1/11/26` (2-digit year), `46327`, text |
| `T` time | Written as `hh:mm` (`8:30` becomes `08:30`), reported | Not a time; seconds other than `00` |
| `U` time | Written as `hh:mm:ss` (`8:30` becomes `08:30:00`), reported | Not a time |
| `S`, `H`, `I` and others | Written as typed: no comma conversion, no amount, date or time warnings | Longer than the length of the rubriek (when that is under 50; over 50 is the truncation warning) |

The current list has no standard PS/DV rubriek of type `T` or `U`; the eigen rubrieken of the
municipality do (type `T`).

Further:
- The value is normalized to NFC.
- Control characters (line breaks, tabs) and characters outside Windows-1252 are rejected.

Special characters (tested in `tests/cases/ok-chars-*` for every input encoding):
- Accepted, one byte each: all accented letters used in Dutch (`á à â ä é è ê ë í ì î ï ó ò ô ö ú ù
  û ü ç ñ ý ÿ` and capitals), `€ ’ ‘ “ ” „ – — … ½ ° § ß æ œ ø å Š Ž £`, and all ASCII punctuation.
- Letters typed as base letter + combining accent are combined first, so they still take one byte.
- Rejected with an error: characters outside Windows-1252, for example the `ĳ`/`Ĳ` ligature, Polish
  `Ł ł ę`, Turkish `Ş ş`, `ő`, `Ć`, Vietnamese `ễ`, Greek, `₂`, `→`, zero-width space and emoji.
  Write `ij` as two letters.
- **Unverified: 0x80-0x9F and 0xFF** (`€ ‚ ƒ „ … † ‡ ˆ ‰ Š ‹ Œ Ž ‘ ’ “ ” • – — ˜ ™ š › œ ž Ÿ ÿ`). In the
  processing report of probe round 4 they were missing (`d’Ancona` showed as `dAncona`, `a€b` as `ab`),
  but the Beaufort GUI accepts `€ ’ “ ” – — …` when typed (owner). Whether the import really loses them
  is not known: it may be the report only. Retest in #20. The script accepts them and keeps doing so
  (owner). 0xA0-0xFE, so all accented letters except `ÿ`, arrived unchanged.
- Values over 50 characters are truncated with a warning.
- For an eigen rubriek, dates, times and uppercase-only values are written as typed. The owner chose
  not to force a format there; Beaufort validates it against the rubriek.

The Excel tool's *Rubriek* tab assigns each rubriek a gegevenssoort and a type. The type drives the
value check: `N` numeriek (default; must be numeric), `S` tekst (free), `D` datum (rewritten as
`dd-mm-yyyy`), `T` tijd (rewritten as `hh:mm`). `H` hoofdletters is listed but has had no effect since
2005. In `N`, `D` and `T` an empty cell was an error; `NULL` wrote an empty value. The list has 1023
rubrieken: 846 `N`, 133 `S`, 42 `D`, 1 `H`. The script's own list comes from the Beaufort export instead
(see [Standard rubrieken](#standard-rubrieken)) and treats `H` as text.

### Productiesoort
The docs list `NOR` and `JWP`; the Excel tool also names `COR`, which is valid in Beaufort (owner). The
script supports `NOR` and `COR`; an empty value becomes `NOR` (the Excel tool wrote 3 spaces).

### Verrekenperiode
Format `ppjjjj` (pp = periode, jjjj = jaar), for example `132003`. Periods 13-15 are only applied if the
ingangsdatum is in December; otherwise Beaufort recalculates. For recalculation over a
jaarwerkperiode the ingangsdatum must equal the start of the last loonperiode. Not implemented:
always 6 spaces. The Excel tool required exactly 6 characters and wrote them as typed.

## Excel tool

How the official Excel tool (V 06.12.6) built a record, from its source. VBA builds the Object_id; the
rest are formulas on a hidden sheet, concatenated into one 187-character cell and saved as text.

| Field | Excel tool | This script |
|---|---|---|
| Procescode | uppercase, right-aligned in 3 | uppercase, left-aligned (same for 3 characters) |
| Rubriek | uppercase, right-aligned in 6 | uppercase, 1-6, left-aligned (#25) |
| Object_id | parts right-aligned, leading zeros kept | same layout, leading zeros stripped (decision 4) |
| Creatiedatum, ingangsdatum | 3 spaces + `ddmmyyyy`; an empty date gave 11 spaces | same; empty is an error |
| Creatiegebruiker | right-aligned in 16, not uppercased | same |
| Waarde | left-aligned; over 50 characters the record became `#WAARDE!` | left-aligned; truncated with a warning |
| Comma in an amount | every comma in any numeric-looking value, silently (`1.234,56` became `1.234.56`) | simple decimals only, other shapes warned (decision 8) |
| Productiesoort | right-aligned in 33, empty gave spaces | 30 spaces + `NOR`/`COR` |
| PS or DV key | from the rubriek list (a PS rubriek ignored a filled dv) | from Dienstverband being filled; for a standard rubriek a mismatch is an error |
| Unknown rubriek | flagged (not in its list) | allowed without a message (eigen rubriek) |
| Value by type | `N` numeric, `D` rewritten `dd-mm-yyyy`, `T` rewritten `hh:mm` | the same for a standard rubriek (also `U` `hh:mm:ss`), checked against its length and decimals; an eigen rubriek as typed with warnings |

Bugs that make its output unfit as a reference beyond the plain cases:
- **Encoding depends on the save path.** Accepting the suggested folder saved as `xlText` (ANSI, Windows-1252);
  choosing another folder saved as `xlTextMSDOS` (the OEM code page, 850 on Dutch Windows, where `é` is
  0x82 and `€ ’ “ ” –` do not exist). So the tool gives no evidence either way about those characters
  in Beaufort (#20).
- **Excel quotes cells when saving text.** A Waarde with `"`, `;` (the Dutch list separator) or a tab was
  written as `"…"` with doubled quotes, so the record grew and the fields after it shifted (checked in
  Excel 16).
- **Dutch regional settings only.** The date formula uses `ddmmjjjj`; with English settings it wrote
  `jjjj` literally.
- **Row counting.** An empty row in the middle gave an empty record and dropped the last row; validation
  counted another column than the export, so some rows could be exported unchecked.
